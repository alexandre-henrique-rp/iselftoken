## 2. Mudança 1 — Batch Paralelo em `payment.cron.ts`

### 2.1 Problema

O método `expirePendingPayments()` (`backendnode/src/api/payment/payment.cron.ts`) processava **até 100 candidates sequencialmente** via `for...of`:

```typescript
// ANTES (sequencial)
for (const payment of candidates) {
  if (payment.txid && this.featureFlags.efiEnabled) {
    const efiStatus = await this.efiPixAdapter.getPix(payment.txid);  // I/O bloqueante
    ...
  }
  await this.prisma.payment.updateMany({ ... });
  ...
}
```

**Impacto:** A cada 15min, 100 calls EFI HTTP em série bloqueiam o event loop. Se cada chamada leva ~500ms, são **50 segundos de bloqueio contínuo**, impedindo outras requests e outros crons.

### 2.2 Solução — `Promise.allSettled` paralelo

```typescript
// DEPOIS (paralelo)
const results = await Promise.allSettled(
  candidates.map((payment) =>
    this.processPaymentCandidate(payment, expirationFilter, now),
  ),
);
for (const result of results) {
  if (result.status === 'fulfilled') {
    expired += result.value.expired;
    reconciled += result.value.reconciled;
  }
}
```

**Refatoração adicional:** corpo do loop extraído para `private async processPaymentCandidate(payment, expirationFilter, now): Promise<{ expired, reconciled }>`.

**Impacto esperado:**
- 100 calls EFI paralelas → reduzido para **~1-2s** (limitado pelo I/O HTTP, não pelo event loop)
- Outras requests não são bloqueadas durante o cron
- Falha em um candidato não afeta os outros (`allSettled`)

### 2.3 Validação

```
PASS src/api/payment/payment.cron.spec.ts (7.654 s)
Tests: 4 passed, 4 total
```

Todos os 4 testes do `expirePendingPayments` (EXPIRED vs CANCELED) passam após refatoração. Comportamento externo idêntico.

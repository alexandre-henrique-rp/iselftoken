### 2.1 Cache Redis em `admin-dashboard-summary.service.ts`

**Fix proposto (não aplicado):**
```diff
+ private readonly CACHE_KEY = 'admin:dashboard:summary';
+ private readonly CACHE_TTL_MS = 30_000;
+
  async getSummary() {
+   const cached = await this.redis.get(this.CACHE_KEY);
+   if (cached) return JSON.parse(cached);
    // ... 29 queries Prisma em Promise.all
+   await this.redis.set(this.CACHE_KEY, JSON.stringify(result), 'PX', this.CACHE_TTL_MS);
  }
```

**Bloqueio:** `backendnode/AGENTS.md` proíbe explicitamente (linhas 263-264):
> "Cache: Redis (`@nestjs-modules/ioredis`) APENAS para session (`session:{userId}`). TTL 7d. **Não usar para outras finalidades (resiliência, invalidação)**."

**Justificativa do bloqueio:** A política é defensiva — cache de negócio exige estratégia de invalidação robusta (mutations em admin devem invalidar o cache). APLICAR esta otimização requer:

1. Decisão humana para atualizar `AGENTS.md`
2. Estratégia de invalidação documentada (qual mutation invalida qual cache key)
3. Migration para invalidar cache quando admin mutar payments/investments
4. Monitoramento de cache hit rate via Sentry

**Workaround aplicado:** índices Prisma + take defensivo reduzem o risco de OOM e melhoram queries subjacentes.

**Decisão recomendada:** Para AGORA, manter como está. Para PRÓXIMA SPRINT, criar proposta de "cache de leitura curta" em `CASE.md` com estratégia de invalidação e atualizar `AGENTS.md`.
